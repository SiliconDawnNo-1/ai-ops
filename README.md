# ai-ops · 能力评测内核（Subsystem A）· v2

> **一句话**：把你用 AI 犯的错，变成可重跑、可测量的能力资产；让 agent 每周被评测、被进化、**且进化动作本身被核销**，而不是靠印象打分。
> 这是一个可以**冷启动**的自进化系统：读完本 README，任何人 + 一个新开的 agent 会话即可从 0 跑起来（agent 入口见 `AGENTS.md`）。

---

## 1. 这是什么

### 要解决的问题
纠错进 memory 是**散文**——不可重跑、不可比较、无法断言。没有评测标准就没有适应度函数，系统只会堆积、不会进化（"不能共产主义"）。

### 解法：MMV 三递归环（v2）
v1 建立了「案例→判分→账本→趋势」的测量环；v2 按 2025–2026 前沿 RSI 研究（DGM/AlphaEvolve/Absolute Zero/AI co-scientist 等，见 spec v2 §2）补上了**修改回流**与**元层测量**：

```
L1 任务环：wyf + agent 干真实活 ──产出──► 真实产物（滞后判分样例）
                                                      │
L2 进化环（周仪式，单线程）                             ▼
  /benchmark（测量）──► ledger ──► SCORES.md（趋势Δ+报警+校准+实验）
       │ 实验核销（到期卡对分兑现，你确认）         │ 报警
       ▼                                        ▼
  /evolve（变异提案+起草实验卡）──► 你审批（选择压力）
       ▼
  基因组：CLAUDE.md / skills / memory / cases / rubrics
                                                      ▲
L3 元进化环（月/季）：预测命中率 · 判分稳定性 · 人机分歧 · type 命中率
       └── 修正评估器与进化策略本身 ◄──────────────────┘
```

- **评测 = case 通过/分数**；**进化 = 按 ROI 修剪/升级，且每笔可验证动作挂一张实验卡**；**你永远是最终裁判**。
- RSI 的落点：L2 的输出改变 L1 的表现，L3 的输出改变 L2 的决策质量——测量是唯一的传递介质。

### 属于更大的系统
这是 AI&Company 自进化系统的**子系统 A（适应度函数）**。整体方法论（六支柱）见 `docs/superpowers/specs/2026-08-16-benchmark-core-design.md` 附录 A；v2 设计（前沿沉淀 → 终极思想 → 打分对比）见 `docs/superpowers/specs/2026-08-30-rsi-v2-design.md`。

## 2. 核心功能（6 组件 + 2 命令 + 1 脚本）

| 组件 | 路径 | 作用 |
|---|---|---|
| 案例 | `benchmarks/cases/` | 11 条：4 条 judged（需判分）+ 7 条 scripted（纯断言，v2 新增 vf-002 自校验） |
| 判分卡 | `benchmarks/rubrics/` | 4 张：洞察链 / 诊断归因 / 长任务元复盘 / 跨领域范式；**v2 各带 `## 校准锚`（真实产物分位锚）** |
| 账本 | `benchmarks/ledger/` | 每次运行原始分数（jsonl）+ 趋势表 `SCORES.md`（v2：报警/趋势Δ/校准/实验四节） |
| **实验卡** | `benchmarks/experiments/` | **v2 新增**：进化动作的基因谱系（假设/成功标准/期限/核销结果），规则见其 README |
| 纠错箱 | `pending-reviews/` | 复发纠错备选案例，周复盘三选：转正/丢弃/退回 |
| 复盘卡 | `retrospectives/` | 长/复杂任务完成的元复盘（归因+最佳实践+实验建议） |

| 命令 | 作用 |
|---|---|
| `/benchmark` | **实验核销**（到期卡对分兑现）→ 三选纠错箱 → 遍历案例（断言/滞后判分+复判探针）→ 报警回流 → 写账本 → 聚合 → commit |
| `/evolve` | 读趋势 → 五类进化动作决策单（每笔起草实验卡）→ 你审批执行；no-data ≥3 期维度必须出题或退休 |

聚合脚本：`benchmarks/lib/group_scores.py`（纯标准库；`due` 子命令出核验队列）。
安装脚本：`bash benchmarks/lib/install_commands.sh`（一键装双宿主）。

### 命令装在哪（双宿主，v2 修 D6）
- Claude Code：`~/.claude/commands/{benchmark,evolve}.md`
- ZCode：`~/.zcode/skills/{benchmark,evolve}/SKILL.md`（安装后新会话生效）
- 仓库内 `.claude/commands/` 与 `.zcode/skills/` 是单一事实源，改协议改仓库、再跑安装脚本。

## 3. 冷启动（0 → 有分，约 1 小时）

**前置**：已装 Claude Code 或 ZCode；本目录已就位（自己建或 `git clone` 朋友的副本）。

1. **装命令**：`bash benchmarks/lib/install_commands.sh`。
2. **确认判分样例约定**：judged 案例每周从**最近真实产物**判分（调研报告 / 复盘卡 / 范式卡），当次产物路径写进 run 的 `evidence_ref`。没有约定的话，系统会记 `no-data` 并提示补样。
3. **跑第一次 `/benchmark`**（在任意目录执行）：
   - 实验核验：空台账跳过；
   - 纠错箱三选：空箱跳过；
   - scripted 案例自动跑断言（检查点/底库健康/交付完整/仓库自校验）；
   - judged 案例取最近真实产物判分（先对 rubric 校准锚）→ **你逐条审批**（你是终局裁判，改分直接说）。
4. **得首张 `SCORES.md`**：judged 有分、scripted 有通过率——这是基线，之后的每次 run 都能对比趋势（Δ 列）。
5. **周仪式做下去**（见 §4），每月跑 `/evolve` 开始进化；第一笔批准的进化动作会诞生你的 exp-001。

> 第一次跑如果脚本断言失败：先看「4.2 读分」判断是环境路径问题还是真违例，别急着修代码。

## 4. 周仪式（每周 ~25 分钟）

1. **归纳本周纠错**：把「再犯的错」写进 `pending-reviews/` 一条（`场景 + 证据 + 是否复发`）。一次性错误**不写**（采样门槛）。
2. **`/benchmark`**：实验核销 → 三选纠错箱 → 判分 → 报警回流 → 你审批 → 自动聚合 + commit。
3. **`/evolve`**：看趋势 → 五类动作（每笔挂实验卡）→ 你勾选 → 执行 → commit。
4. **检查 `SCORES.md`**：报警节置顶（有异常只看它），趋势 Δ 看方向，实验节看进化动作是否兑现。

### 4.1 纠错 → 案例的表达规则
- **一次性错误** → 只进 memory，不建 case（不符合采样门槛：不会再现）。
- **复发错误** → 写 pending 一条，周复盘转正成 case。转正三问：会再现吗？判分能防回归吗？固定成本 < 复用价值？

### 4.2 读 `SCORES.md`（v2 四节）

```
## 报警   ← 有异常只看这节：回归 / 跌破通过线 / no-data 连续≥3期 / 到期实验卡
## 趋势   ← 维度表 + Δ上轮（judged 分数变化方向）
## 校准   ← 上轮 prediction 待核验清单 + judge 标签分布（agent-selfgrade vs user）
## 实验   ← 卡片状态计数 + type 命中率（哪类进化动作真的有效——L3 元层输入）
```

- **judged 分**（洞察链/诊断归因/长任务元复盘/跨领域范式）：规则为「≥3.5/5 通过」；连续 4 周低于通过线 → 该维度的方法要修（`/evolve` 修剪/升级）。
- **脚本通过率**：纪律性（提交规范/检查点/底库健康/交付完整/仓库自校验）是否守住，低于 100% 就是有违例要追（报警会自动开箱）。
- 分数是**先行指标**，你真实体感是**滞后指标**：两者背离时跑 `/evolve` 补漏（防指标被玩坏）。

## 5. 分享给朋友（冷启动给另一个人）

1. **整个 `~/Desktop/code/ai-ops` 目录即全部**。对方 `git clone`（或拷贝）后按 §3 冷启动五步走。
2. **必须适配的硬编码**：scripted 案例的断言里写死了 `~/.claude`、`~/Desktop/code/document`、`~/Desktop/code/ai-ops` 三个路径——对方改成自己的路径，或先手动跑几遍脚本案例确认。
3. **判分卡是纯方法论**（可通用，不用改；校准锚样例路径需换成自己的产物）；**案例里脚本断言是自己的基建**（需适配）。
4. 建议对方先跑 2-3 周自己的真实任务，把 judged 判分从「我的纠错」稀释成「他的纠错」，再谈进化。
5. 对方如果也是 agent 重度用户：直接把 `AGENTS.md` 扔给 agent，按其中复刻协议走一遍研究→设计→重构流程。

---

## 6. 成功标准（6 周后自查）

1. 重复纠错案例开始变少（系统在积累）。
2. 真的执行过修剪 / 升级动作，**且实验卡核销过 verified/failed**（系统在进化，不是摆设——v2 加严）。
3. 你花在「评价 agent」上的注意力下降（系统在替你打分，报警自动开箱）。
4. 你能一句话回答「我的 agent 哪强哪弱、分数依据是什么」，**并报出哪类进化动作命中率最高**。
