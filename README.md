# ai-ops · 能力评测内核（Subsystem A）

> **一句话**：把你用 AI 犯的错，变成可重跑、可测量的能力资产；让 agent 每周被评测、被进化，而不是靠印象打分。
> 这是一个可以**冷启动**的自进化系统：读完本 README，任何人 + 一个新开的 Claude Code 会话即可从 0 跑起来。

---

## 1. 这是什么

### 要解决的问题
纠错进 memory 是**散文**——不可重跑、不可比较、无法断言。没有评测标准就没有适应度函数，系统只会堆积、不会进化（"不能共产主义"）。

### 解法
四层闭环，把「经验」变成「组织能力」：

```
纠错/成功/复盘 ──► 案例(cases，可重跑) ──► 判分(脚本断言 + rubric) ──► 账本(ledger) ──► 趋势(SCORES.md)
     ▲                                                                                │
     └──────── 进化(/evolve：修剪/升级/补漏) ◄──────── 你审批 ◄────────────────────────┘
```

- **评测 = case 通过/分数**；**进化 = 按 ROI 修剪/升级**；**你永远是最终裁判**。

### 属于更大的系统
这是 AI&Company 自进化系统的**子系统 A（适应度函数）**。整体方法论（六支柱）见 `docs/superpowers/specs/2026-08-16-benchmark-core-design.md` 附录 A。

## 2. 核心功能（5 组件 + 2 命令 + 1 脚本）

| 组件 | 路径 | 作用 |
|---|---|---|
| 案例 | `benchmarks/cases/` | 10 条：4 条 judged（需判分）+ 6 条 scripted（纯断言） |
| 判分卡 | `benchmarks/rubrics/` | 4 张：洞察链 / 诊断归因 / 长任务元复盘 / 跨领域范式 |
| 账本 | `benchmarks/ledger/` | 每次运行原始分数（jsonl）+ 趋势表 `SCORES.md` |
| 纠错箱 | `pending-reviews/` | 复发纠错备选案例，周复盘三选：转正/丢弃/退回 |
| 复盘卡 | `retrospectives/` | 长/复杂任务完成的元复盘（归因+最佳实践+实验建议） |

| 命令 | 位置 | 作用 |
|---|---|---|
| `/benchmark` | `~/.claude/commands/benchmark.md` | 三选纠错箱 → 遍历案例（脚本断言 / rubric 判分）→ 写账本 → 聚合 → commit |
| `/evolve` | `~/.claude/commands/evolve.md` | 读趋势 → 出五类进化动作（修剪/升级/补漏/实验提案/更高价值问题）→ 你审批执行 |

聚合脚本：`benchmarks/lib/group_scores.py`（纯标准库，无依赖）。

## 3. 冷启动（0 → 有分，约 1 小时）

**前置**：已装 Claude Code；本目录已就位（自己建或 `git clone` 朋友的副本）。

1. **确认判分样例约定**：judged 案例每周从**最近真实产物**判分（调研报告 / 复盘卡 / 范式卡），当次产物路径写进 run 的 `evidence_ref`。没有约定的话，系统会记 `no-data` 并提示补样。
2. **跑第一次 `/benchmark`**（在任意目录执行，命令内部有根路径）：
   - 纠错箱三选：空箱跳过；
   - scripted 案例自动跑断言（检查点/底库健康/交付完整）；
   - judged 案例取最近真实产物判分 → **你逐条审批**（你是终局裁判，改分直接说）。
3. **得首张 `SCORES.md`**：judged 有分、scripted 有通过率——这是基线，之后的每次 run 都能对比趋势。
4. **周仪式做下去**（见 §4），每月跑 `/evolve` 开始进化。

> 第一次跑如果脚本断言失败：先看「4.2 读分」判断是环境路径问题还是真违例，别急着修代码。

---

## 4. 周仪式（每周 ~30 分钟）

1. **归纳本周纠错**：把「再犯的错」写进 `pending-reviews/` 一条（`场景 + 证据 + 是否复发`）。一次性错误**不写**（采样门槛）。
2. **`/benchmark`**：三选纠错箱 → 判分 → 你审批 → 自动聚合 + commit。
3. **`/evolve`**：看趋势 → 五类动作（含升级到 CLAUDE.md / skill / memory）→ 你勾选 → 执行 → commit。
4. **检查 `SCORES.md`**：维度趋势是否守住通过线。

### 4.1 纠错 → 案例的表达规则
- **一次性错误** → 只进 memory，不建 case（不符合采样门槛：不会再现）。
- **复发错误** → 写 pending 一条，周复盘转正成 case。转正三问：会再现吗？判分能防回归吗？固定成本 < 复用价值？

### 4.2 读 `SCORES.md`

| 维度 | 运行次数 | judged平均分 | 最新分 | 脚本通过率 |
|---|---|---|---|---|
| reasoning-depth | 3 | 3.8 | 4.2 | — |

- **judged 分**（洞察链/诊断归因/长任务元复盘/跨领域范式）：规则为「≥3.5/5 通过」；连续 4 周低于通过线 → 该维度的方法要修（`/evolve` 修剪/升级）。
- **脚本通过率**：纪律性（提交规范/检查点/底库健康/交付完整）是否守住，低于 100% 就是有违例要追。
- 分数是**先行指标**，你真实体感是**滞后指标**：两者背离时跑 `/evolve` 补漏（防指标被玩坏）。

## 5. 分享给朋友（冷启动给另一个人）

1. **整个 `~/Desktop/code/ai-ops` 目录即全部**。对方 `git clone`（或拷贝）后按 §3 冷启动五步走。
2. **必须适配的硬编码**：scripted 案例的断言里写死了 `~/.claude`、`~/Desktop/code/document`、`~/Desktop/code/ai-ops` 三个路径——对方改成自己的路径，或先手动跑几遍脚本案例确认。
3. **判分卡是纯方法论**（可通用，不用改）；**案例里脚本断言是自己的基建**（需适配）。
4. 建议对方先跑 2-3 周自己的真实任务，把 judged 判分从「我的纠错」稀释成「他的纠错」，再谈进化。

---

## 6. 成功标准（6 周后自查）

1. 重复纠错案例开始变少（系统在积累）。
2. 真的执行过修剪 / 升级动作（系统在进化，不是摆设）。
3. 你花在「评价 agent」上的注意力下降（系统在替你打分）。
4. 你能一句话回答「我的 agent 哪强哪弱、分数依据是什么」。
